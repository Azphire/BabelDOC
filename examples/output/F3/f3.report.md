# F3 — 五日修复周期收官

本报告是收口件,不是批次件:本次会话不加任何机制。它做三件事——把本周期一直推
迟的门禁历史(sweep 集)跑完、把全语料再跑一遍并给每个 stage 计时、把周期的文档
欠账结清。

运行序按裁定执行:**全量预热跑(cold,不计时)→ sweep 集补跑(一次一个,杀前留
log)→ 温缓存全量六样张(warm,阶段计时 sidecar 开启)**。

驱动 `examples/output/F3/scripts/run_f3.py`;门禁 `spec_checks/spec_check_f3.py`,
按 §5.3 全量写(W-B10-02 到期)。

## 4. 评测协议修订:"修复环绕过缓存 = 唯一不可重放段"作废

`docs/eval/metric_contract.md` §2f 已改写。作废理由是三份证据,时间序:

1. **b10.2 T3 修掉了成因** —— 决策键改取请求的一个投影,丢掉
   `volatile_evidence_keys` 声明的逐运行字段;`CACHE_KEY_VERSION` 升到 2。
2. **b10.4 R1 钉死了"跨跑差异"的真正成因** —— 同一份代码两跑,请求集逐条相同,

3. **F3 是整语料检验** —— 六样张两臂,`api_calls` 全 0,修复照常施加。

现行条款:**不存在按设计不可重放的环节;可重放性等价于请求集是否稳定**。三条推论
各自可断言:A/B 的预热臂(第一臂若产生首见请求且答案进入下游文本,两臂不可比)、
采样方差仍在但位置变了(它属首次采样而非重放)、键的版本是证据的一部分(升版后第
一跑必然全未命中)。

## 10. 性能:阶段计时与 b11 靶单

温缓存臂,六样张 41 页,墙上时间 **357.8s**,归属到 stage 的 **83.4s**。

| stage | 秒 | 占墙上时间 |
| --- | --- | --- |
| Parse Page Layout | 23.7 | 6.6% |
| Subset font | 19.6 | 5.5% |
| Save PDF | 18.3 | 5.1% |
| Translate Paragraphs | 8.0 | 2.2% |
| Parse PDF and Create Intermediate Representation | 4.9 | 1.4% |
| Parse Paragraphs | 2.9 | 0.8% |
| DetectScannedFile | 1.7 | 0.5% |

**最大的一个发现**:声明的流水线 stage 只解释了不到四分之一的墙上时间,其余
**77%** 落在所有 stage 窗口之外 —— checkpoint 序列化、挂在
stage 边缘上的十余个扩展 pass、模型装载、PDF 生成的收尾。**靶单的第一条不是某个
stage 慢,而是"最大的一块没有名字"**。

b11 靶单(按本轮实测排序):

1. **缓存温度差**:Courier-en 单臂 **378s → 55s**,同 stack、同输入,差别只在缓存
   温度与机器负载。任何性能主张必须先声明温度。
2. **未归属时间**:77% 的墙上时间不在任何 stage 里。第一步是把
   扩展 pass 与 checkpoint 写盘各自装上计时,而不是先去优化最慢的 stage。
3. **gate cache 的 LRU 根修**:16GB 上限之下,一次 sweep 反复"建一个、逐两个"。
   本次 sweep 全程可见 `gate cache swept before publishing …`。
4. **指纹的字节粗粒度**:一次语义为零的编辑(把配置里的字符写成等价转义)使整份
   gate cache 失效并触发全量重建。这是安全的方向,但代价是可量的,应当有一条"按解
   析形态入指纹"的可选路径。
5. **sweep 并行化**:18 档 sweep 门禁串行执行,而多数时间花在互不相干的构建上。
